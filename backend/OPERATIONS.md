## Identity

Staff tokens remain `/api/auth/login` tokens. Portal tokens only authenticate `/api/portal/*`, and cannot access staff or old CRM APIs. Portal profiles have a primary key on customer_id and unique username; each profile has one contact_name/email/phone/company_address. Provision through staff-admin `POST /api/operations/customers`, optionally linking an existing customer_id. Historical multiple-contact rows remain historical; new portal operations use only the single portal profile.

`POST /api/portal/login {username,password}` → token; GET me, POST logout. GET catalog returns published product series with `price_rule` or null. GET orders and consumption are company-scoped.

Staff `POST /operations/customers/{cid}` edits company/contact_name/email/phone/company_address without creating another contact or rewriting order snapshots. Portal catalog includes source_code/configuration_schema/orderable/scope. The schema lists key/labels/choices/required/type. Raw source price matrices are omitted from portal catalog, calculations and order responses. Template-only products are excluded from the public product endpoints. Ashwood is display-only until a template rule exists.

## Orders and rules

`POST /api/portal/price` and `/api/portal/orders` accept project_name, site_address, submission_key, installation_required and lines `{window_name, product_id, width_mm, height_mm, quantity, panel_count, options}`. Quantity counts repeated windows; panel_count counts panels per window. Legacy unconfigured products may be saved pending_review with total=null, but cannot be invoiced. Imported display-only/missing/invalid matrix configurations are rejected. No client unit_price, discount or surcharge is accepted.

Imported shutters: area rounded upward to 2dp, minimum 0.5m², area rate plus product surcharge. Other blinds: next-greater-or-equal width/drop matrix lookup. Apply staff discount, then round the line unit upward to 2dp, multiply by repeated-window quantity. Installation uses the source per-panel/per-product rate plus surcharge, quantity, and order minimum when selected. GST retains source precision; currency display uses 2dp, and the 60% deposit rounds the precise total upward. Results include subtotal/installation/tax/total/deposit/rule_version and per-line prices. The provided ClearPVC installation alias mismatch remains an explicit import warning and blocks that installation quote.

Staff-only `POST orders/{id}/adjust {note,lines:[{line_id,discount,product_surcharge,installation_surcharge}]}` accepts a source-listed discount and a meaningful note before review, recalculates and records history. Reviewed projects cannot be adjusted through this endpoint. Price-rule imports never rewrite existing snapshots.

Admin `POST /api/operations/pricing/{product_id}` accepts PriceRule in operations.py. Rules require evidence of the confirmed sheet, area/minimum/rounding/dimension limits, currency/tax_basis and exact option choices. The supported formula is explicitly selected: round dimensions upward by dimension_step_mm, area in m² subject to minimum; `(area * rate + sum fixed) * (1 + sum percent / 100) + sum installation`, rounded per unit then multiplied by quantity. An empty charge dictionary is a visual-only choice. This formula is an available configuration, **not a claim that the customer's unprovided sheet uses it**. No rules are seeded. Submit snapshots configured prices; review can price a previously unpriced pending order. Reviewed snapshots never change with the catalog.

Staff GET orders; POST orders/{id}/review generates one 60% deposit invoice draft; POST deposit-received records independent manual confirmation with actor/time. POST supplier-order `{reference}` requires that confirmation. Supplier Excel export returns 409 until the actual template/mapping is supplied. GET `orders/{id}/production-sheet` and `job-sheet` produce macro-free XLSX files from the accepted snapshot, with typed dimensions/quantities and full configuration details. The production document is clearly labelled a draft, and contains no old source customer rows. Both require staff authentication.

POST transit `{order_ids,operation_key}` gives per-order success/failed/skipped. POST fulfilment `{order_id,kind:'arrival'|'delivery',operation_key,lines:[{line_id,quantity}]}` records the actual batch. Repeat identical operation keys do not duplicate; altered bodies conflict. Arrival ≤ ordered; delivery ≤ arrived. History keeps each batch; arrival_status/delivery_status/payment_status are separate. Frontend batch selection can submit per-order requests and display each outcome.

## Invoice, email and rebate boundaries

GET invoices, GET notifications; POST invoices/{id}/send explicitly sends a stable text invoice to the sole contact. This is a workflow prototype, not a confirmed statutory invoice layout/PDF. Arrival saves an outbox event then automatically attempts the email, showing only that batch. Statuses: pending/sending/sent/not_configured/delivery_unknown. Repeated calls never resend a sent or ambiguous email. POST notifications/{id}/retry is available after not_configured is fixed; ambiguous SMTP outcomes require manual mailbox reconciliation. A process interrupted while sending leaves `sending`, requiring that same reconciliation. Never label these as successfully sent.

POST rebates imports a confirmed monthly credit result with customer_id, source_order_ids, month, amount, currency and evidence. A source order cannot be counted again. There is no invented monthly ladder or automatic accrual formula. GET rebates explicitly reports confirmed_monthly_rules_required.

POST settlements takes order_ids, operation_key, rules_evidence and billing_basis=`fully_delivered_remaining_total`. It only supports fully delivered, deposit-confirmed projects of one company/currency/tax_basis; partial-arrival billing is blocked pending rules. It deducts actual saved deposits and eligible prior-month confirmed rebate balances; allocations and invoice claims are atomic. It never opens full balances merely because one batch arrived. POST `invoices/{id}/received {note}` records manual balance receipt once, with actor/time, and marks its projects paid. Deposits still use the project-specific confirmation. Automatic monthly tiers, expiry/cancellation/refund rules, invoice corrections and confirmed invoice layout remain dependent work.

GET `/portal/consumption` and staff `/operations/customers/{cid}/consumption` return orders/invoices/rebates and currency-separated summary: ordered, invoiced, manually confirmed received and outstanding_invoiced. Unpriced projects are counted separately. These are explicit operational definitions, not a guessed rebate basis. Dashboard real analytics and customer ratings stay deferred per v5.
